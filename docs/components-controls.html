Components — Controls

Interactive elements that trigger actions or accept user input. All pure CSS unless noted — no JS required.

Buttons
Button variants
Five visual weights from high-emphasis filled to low-emphasis text. Pick the weight that matches the action's prominence. Add a leading <span class="icon"> for an icon.
tips_and_updates
When to use each variant Use Filled for the single primary action on a surface (save, submit, create). Use Tonal for secondary actions that are still fairly important. Use Outlined for actions that need a boundary but not strong emphasis (cancel, back). Use Text for the lowest-emphasis option when context makes the action obvious. Use Danger to signal a destructive, irreversible action — pair it with a confirmation dialog. Don't place two filled buttons side by side; one should always be the primary.

Markup reference: README §4 — Buttons · Classes: .btn + --filled --tonal --outlined --text --danger · Sizes: --sm --lg

Icon buttons
Icon-only actions
For compact, toolstrip-style actions where the icon alone communicates intent. Always include an aria-label or title attribute for accessibility.
tips_and_updates
When to use Use icon buttons in toolbars, card headers, and dense table rows where labelled buttons would consume too much space. Use the filled variant as a mini-FAB for a contextual primary action. Use selected for toggle actions (favourite, bookmark, pin) that have an on/off state.

Classes: .icon-btn + --filled --selected --sm

Split button
Primary action + overflow menu
A filled button split into a main action and a dropdown arrow. JS wires the dropdown via data-menu-toggle — no init call needed.
tips_and_updates
When to use Use a split button when there is one clear primary action alongside 2–5 secondary variants of that action. Good examples: "Create task" with options to also assign or save as draft; "Export" with options for CSV, PDF, or JSON. Avoid it when the variants are unrelated — use a menu button instead.

Requires immaterial.js. Wrap with [data-menu-wrap], arrow carries data-menu-toggle.

Segmented buttons
Single-select control group
Pure CSS — driven by radio inputs. The selected option shows a leading checkmark automatically. No JS needed.
tips_and_updates
When to use Use segmented buttons for 2–5 mutually exclusive view or filter options that are always visible — time ranges, chart granularity, density levels, theme selection. Prefer this over a dropdown when all options should be scannable at once and switching is frequent. For longer or dynamic option lists, use a select field or chips instead.

Classes: .segmented · .segmented__option (wraps a radio input) · .segmented__check (the checkmark icon — always present, revealed by CSS on checked state)

Connected button group
Fused toggle buttons
Icon or labelled buttons fused at their borders. Toggle .is-active on the selected segment via a few lines of JS.
tips_and_updates
When to use Use a connected button group for compact binary or ternary toggles in toolbars — density, view mode (grid/list), text alignment. For more than 4 options or when options have labels as well as icons, switch to a segmented control. The button group looks best with icons only (button-group--icons).

Classes: .button-group + --icons · Mark the active button with .is-active

Chips
Filter & assist chips
Filter chips toggle .is-selected to represent an active filter. Assist chips are static suggestion links. Both accept a leading icon.
tips_and_updates
Filter chips — when to use Use filter chips when users need to narrow a list by multiple independent categories (e.g. HVAC + Electrical + High priority), and when none, some, or all can be active simultaneously. Chips are better than segmented buttons here because multiple can be selected at once.

Assist chips — when to use Use assist chips for contextual, read-only labels — a "Due today" tag, a category label, or a system-generated suggestion. They look like chips but are not interactive.

Classes: .chip + .is-selected for active filter · .chip--assist for static chips

Form inputs
Text fields
The notched label floats on the field border. Its background must match the surface behind the field — var(--surface) inside a card, var(--surface-dim) on the page. All variants wrap in .field.
tips_and_updates
When to use each variant Use the standard field inside cards or on surfaces where the border-break label reads naturally. Use pill for search bars and single-line filter inputs — the rounded shape signals "search" more intuitively. Use small (32px) in toolbars, table headers, or any dense context where a full-height field would dominate — use a placeholder or adjacent label instead of the notched label in this case. Use the select variant when the set of options is fixed and known upfront; prefer chips or a filter dropdown for dynamic or multi-select scenarios.

Notch background note

The label's background must equal the surface it sits on. Inside a card: .field__label { background: var(--surface); } (the default). Directly on the page: override to var(--surface-dim). Getting this wrong leaves a stripe of border across the label text.

Classes: .field + --pill --sm --error --select · Children: .field__label .field__input .field__leading .field__caret .field__error

Slider
Range input
Drag or use arrow keys / Home / End to set a value. JS handles interaction and optionally writes the value to any element via data-output. Listen for 'change' events for custom logic.
tips_and_updates
When to use Use a slider when the user needs to select a value from a continuous or stepped range, and when the relative position within the range is meaningful (e.g. duration, threshold, budget). For small, discrete sets of values, segmented buttons are clearer. For precise numeric entry, use a text field instead — sliders are notoriously hard to hit exactly.

Switch & checkbox
Toggle controls
Both are native inputs styled purely with CSS — no JS, no wrappers beyond a label for the switch. The checkbox check glyph is drawn by CSS.
tips_and_updates
Switch vs. checkbox Use a switch for a setting that takes immediate effect when toggled (turn notifications on, enable a feature flag). Use a checkbox inside a form where the change only takes effect when the form is submitted, or for multi-select within a list. If you have a single on/off option in a form, a checkbox with a label is clearer than a switch.

Classes: .switch wrapping a checkbox input + .switch__track > .switch__thumb · .checkbox on a bare input

Radio buttons
Single-select option list
Native radio inputs styled with pure CSS. Group with .radio-group; wrap each in a .radio-group__option label.
tips_and_updates
When to use Use radio buttons when the user must choose exactly one option from 3 or more choices, especially when the labels are longer than 2–3 words. For 2–4 short, always-visible options, prefer segmented buttons — they are more compact and immediately communicate the current selection. For long or dynamic lists, a select field scales better.

Classes: .radio-group · .radio-group__option (label) · .radio (input)
