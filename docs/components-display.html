Components — Display

Components that communicate state, structure content, or guide users through a workflow. Most are pure CSS; dialogs, toasts, and tabs require immaterial.js.

Badges
Status badges & priority labels
Badges communicate a discrete status. Priority labels use an upward-pointing triangle dot to signal urgency by colour. Both include a quiet dot variant for dense tables.
tips_and_updates
Filled vs. dot variant Use the full badge in card bodies, list items, and detail views where you have space. Use badge--dot in table cells and anywhere four or more badges appear in a single row — the dot reduces visual noise while preserving the colour signal.

Badge vs. priority label Use badges for workflow states (In progress, Done, Draft). Use priority labels only for urgency levels — they use a fixed colour set (red/amber/teal) that carries a universally understood meaning.

Progress
Progress bar & spinner
Linear progress for known-duration tasks; spinner for indeterminate loading states. Set the bar width inline as a percentage.
tips_and_updates
When to use Use a progress bar when you know the percentage of completion — plan completion, upload progress, multi-step forms. Use a spinner for indeterminate operations where you can't quantify progress (API calls, initial page loads, background syncs). Choose spinner size: --sm inline next to a button label, default inside a card, --lg as a full-page loading indicator.
Monthly PM plan68%

Classes: .progress > .progress__bar (width = percentage) · .spinner + --sm --lg

Tabs
Tab navigation
JS switches panels. Wrap tabs and panels in [data-tabs-scope] so switching stays scoped when a page has multiple tab groups. Counts use .tab__count.
tips_and_updates
Line tabs vs. pill tabs Use the default line tabs at the top of a section or page — the underline anchors to the nearest surface edge and reads clearly on --surface-dim. Use pill tabs (tabs--pill) inside cards or on tonal surfaces where a floating underline would look unanchored. Panels are optional — for filter bars, listen for the tabchange event and filter data client-side.

Toolbar
Action bar
A horizontal strip of actions above a card or table. Use .toolbar__spacer to push trailing items right, and .toolbar__divider to group related actions.
tips_and_updates
When to use Use a toolbar above a data table or a card that has several independent actions — density control, column visibility, refresh, export. Keep it to icon buttons for secondary actions; reserve labelled buttons for the single primary action (if any). The toolbar itself has no background — it inherits the surface beneath it.

Classes: .toolbar · .toolbar__spacer (flexible gap) · .toolbar__divider (1px separator)

Breadcrumbs
Hierarchical path
Ancestor links separated by chevron_right icons. The current page is a plain .breadcrumbs__current span, not a link.
tips_and_updates
When to use Use breadcrumbs when the app has 3+ levels of hierarchy and users regularly need to navigate up. Skip them on flat apps, dashboards, or wizard flows where the concept of "going up a level" doesn't apply. Don't duplicate breadcrumbs and a back button — one or the other is enough.

Alerts
Alert banners
Persistent inline messaging for conditions that need ongoing attention. For one-off feedback after an action, use a toast instead. An optional .alert__title and dismiss button are supported.
tips_and_updates
When to use Use alerts for stateful, persistent conditions the user needs to be aware of throughout a session: a degraded connection, a sensor that's been offline for an hour, a scheduled maintenance window. Remove the alert when the condition clears. Don't use alerts for transient action feedback (saved, deleted) — use a toast. Don't stack more than 2–3 alerts; if many conditions need to be surfaced, use a summary list instead.

Dialog
Modal dialog
Markup lives in the page, hidden. Trigger with data-dialog-open="id". Closes on scrim click, data-dialog-close, or Esc. Use Immaterial.openDialog() / closeDialog() for programmatic control.
tips_and_updates
When to use Use a dialog for actions that are irreversible or high-stakes and require an explicit confirmation: deleting records, submitting a form with significant side effects, overwriting data. Keep dialogs to 1–2 actions (confirm + cancel). Don't use a dialog for non-destructive confirmations — a toast with an undo action is less disruptive. Don't use dialogs as forms for more than 2–3 fields; a drawer or a dedicated page scales better.

Toast
Snackbar / toast notification
No markup needed — call Immaterial.toast(). Toasts stack at the bottom of the screen and auto-dismiss. An optional action label (e.g. "Undo") can be passed in the options.
tips_and_updates
When to use Use toasts for brief, non-blocking feedback after a user action: "Task created", "3 items deleted", "Settings saved". Keep messages under ~60 characters. Use the action label for a single recoverable action (Undo, Retry). Don't stack multiple toasts for a single user action — summarise. Don't use toasts for errors that require attention — use an alert banner instead. Set duration: 0 for sticky toasts that require user dismissal.

Requires immaterial.js. Immaterial.toast(message, { actionLabel, onAction, duration }) → returns dismiss()
