Composed patterns

Patterns assembled from core components. They need per-use decisions (anatomy, widths, inline values) and are starting points, not drop-in components.

Cards
Card header treatments
The base card is a raised white surface. A title sits inside it, anchored one of two ways: a divider rule beneath the title, or a filled tonal bar that spans the full width. Wrap in .card--clip when using the filled bar so it honours the card's border radius.
tips_and_updates
Choosing a header treatment Use the divider header (1a) when the card sits on a light background and you want a minimal, clean separation. Use the filled bar (1b) when the card needs stronger visual hierarchy, or when it appears on a darker tonal surface where a hairline divider would be hard to see. Add trailing actions (1c) — icon buttons, a menu — to the divider header when the card has its own controls (filter, refresh, expand). Never add more than 2–3 trailing icons; overflow into a more_vert menu.

Lists
Four list constructions
Choose the list construction based on how much anatomy the content needs. Add .list--interactive when items are clickable.
tips_and_updates
Choosing a construction A (full) — icon + title + meta + trailing. Use when each item has a clear identity and secondary context (activity feeds, notifications, work orders).
B (stripped) — title + trailing only. Use for lighter content where metadata isn't needed (asset name + status).
C (headerless table) — use when values need to align vertically across rows. This is a table--standalone, not a list. Better than a list when you have 2+ data columns per row.
D (tonal panel) — filled surface, no card shadow. Use as secondary/chrome content next to raised cards (sidebars, summary panels).

Data table
Native table with rich features
A native <table> with the table class. Fills its container; columns size to content or can be pinned with <colgroup>. Cells use tabular-nums for clean numeric alignment. Wrap in a card with overflow:hidden for a contained look, or use table--standalone for a borderless card of its own.
tips_and_updates
Table vs. list Use a table when users need to compare values across rows — especially when column headers help interpret the data, or when you have 3+ data points per row. Use a list (construction A or B) when rows have a primary name/title with supporting meta — no comparison across columns needed.

Wiring behaviour Sorting, filtering, pagination, and select-all are application logic — the design system provides the visual states only (is-active on sort headers, is-selected on rows, is-hidden on cells). See the README §7 for wiring recipes.

Bar chart
Flex bar charts
Bars in a flex row; each bar's height is a percentage set inline (0–100% of the chart height). Labels are a matching flex row beneath. Convert your data: height = value / max * 100.
tips_and_updates
When to use Use the vertical bar chart for a simple time series or category comparison where the category names are short (Mon/Tue, months). Use the horizontal variant (progress tracks) when category names are long, when exact values matter alongside the chart, or when comparing 5+ categories — horizontal bars leave more room for labels. For anything beyond simple bars (lines, stacks, scatter) reach for <svg> or <canvas> directly.

Navigation & stats
Sidebar nav & stat cards
A persistent sidebar using .sidebar / .nav-item — the same component this documentation uses. Stat cards sit beside it in a grid, using .stat-card.
tips_and_updates
Sidebar nav Use for apps with 3+ main sections. Group items under .nav-section overline headers. Mark the current page with .is-active. The sidebar itself provides no scroll or responsive behaviour — wrap it in a container with position: sticky; height: 100vh; overflow-y: auto for a fixed left sidebar.

Stat cards Use for KPIs at the top of a dashboard — 3–6 values that summarise the current state. The --accent variant uses the primary container colour to draw attention to the most important metric. The tonal (no border/shadow) variant reads as secondary information.
